Data Safety

先保证不丢，
再谈功能。

Markdown Writing 把本地文件视为唯一事实来源。保存、冲突处理、历史恢复和退出保护都围绕这条原则设计，让每次写入都可解释、可验证。

安全设计 设计原则 保存流程 外部冲突 历史与回收站 退出与恢复 能力边界

设计原则

编辑器的第一责任不是让界面显得智能，而是在异常、误操作和多窗口竞争发生时，尽量不让用户失去已经写下的内容。

  • 本地优先：普通 Markdown 文件保留在磁盘，应用不会把文档锁进私有格式。
  • 写入可验证：每次保存都携带当前 revision 和内容哈希，版本不一致时停止覆盖。
  • 恢复优先于报错：冲突、崩溃和误删除都应提供可执行的恢复路径，而不是只有错误提示。
  • 用户保留决定权：外部修改发生时，可以重新载入、保留本地版本或另存副本。

一次保存经历什么

自动保存和手动保存共用同一条提交路径。这样不会出现“手动保存更安全、自动保存路径不同”的隐性分叉。

01
校验当前版本

提交时携带文档的 revision 与内容哈希，确认应用读取的版本仍是磁盘上的当前版本。

02
写入临时文件

新内容先写到目标目录中的临时文件，避免原文件在写入进行到一半时被截断。

03
原子替换原文件

内容写入完成后替换原文件，再做必要的清理，让读者看到的始终是完整版本。

04
记录版本与恢复状态

保存成功后更新 revision、写入历史快照，并清理已经落盘的崩溃恢复内容。

保存失败不回滚编辑状态

失败时页面继续保持 dirty 状态，恢复快照也会保留。用户可以重试、另存或先复制内容，不会因为一次写盘失败丢失编辑现场。

外部修改与冲突处理

应用会定期检查当前文件的内容哈希和 revision。文件被其他编辑器修改、删除或重命名后，页面会明确说明冲突，而不是继续静默自动保存。

  1. 重新载入：放弃本地未保存版本，读取磁盘上的最新内容。
  2. 保留本地并覆盖：在确认磁盘版本后，用应用中的内容重新提交。
  3. 另存副本：把当前内容保存到新路径，保留双方版本，再决定后续处理。

冲突检查同时适用于普通文件和数据库文档模式，避免两种存储路径逐渐出现不同的覆盖行为。

历史与回收站

版本历史保存最近 50 个自动保存快照。恢复历史版本同样需要提供当前 revision，避免恢复旧内容时覆盖另一个窗口刚刚完成的保存。

场景 保护动作 恢复入口
误覆盖内容 保存前生成历史快照 版本历史中选择“恢复”
误删除文档 文件先移动到应用回收站 回收站中恢复到原路径
外部文件消失 保留当前编辑内容和恢复快照 重新载入或另存本地副本

退出与崩溃恢复

应用在存在未保存内容时，退出流程会先尝试完成保存，并列出仍未落盘的文档。正常关闭后清理对应恢复状态；异常退出则保留下一次启动可读取的轻量快照。

恢复快照包含当前文档、内容、revision、内容哈希、编辑模型版本和最后事务编号。启动时如果检测到未处理快照，会明确询问恢复还是丢弃，不会自动把旧内容覆盖到新文件。

恢复也有版本边界

恢复内容仍需经过当前文档版本校验。如果磁盘文件已经变化，应用会进入冲突处理流程，而不是直接覆盖。

能力边界

这些机制主要防止正常使用中的误覆盖、进程中断和文件竞争。它们不是加密工具，也不能替代操作系统备份。

  • 应用不会把文档上传到云端，网络只在读取 GitHub Releases 等明确功能中被使用。
  • 应用数据目录包含历史版本和回收站元数据，应和其他重要目录一起纳入系统备份。
  • 如果磁盘损坏、权限被拒绝或系统级工具直接改写文件，应用会尽量保留恢复副本并报告失败，但无法保证物理介质本身可恢复。
  • 涉及敏感内容时，应配合加密磁盘、文件权限和可信的备份策略使用。
